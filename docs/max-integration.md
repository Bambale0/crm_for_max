# Диагностика интеграции MAX

Дата проверки официальной документации: **13 сентября 2026**.

Добавлен диагностический клиент для Э0. Он проверяет токен бота, наличие подписок и,
по указанному ID тестового чата, объявленные права. Проверка доставки webhook,
callback, фотографий и работа двух ботов в реальном чате **ещё не выполнены**.
Эта команда не закрывает P-02, P-03 или эпик Э0.

## Подтверждённые контракты

| Метод | Что проверяем | Официальный источник |
|---|---|---|
| `GET /me` | `user_id` и `is_bot`; токен передаётся как `Authorization: <token>`, без `Bearer` | [Информация о боте](https://dev.max.ru/docs-api/methods/GET/me) |
| `GET /subscriptions` | Наличие элементов в массиве `subscriptions` | [Получение подписок](https://dev.max.ru/docs-api/methods/GET/subscriptions) |
| `GET /chats/{chatId}/members/me` | ID бота, `is_admin`, `is_owner`, список `permissions` | [Членство бота](https://dev.max.ru/docs-api/methods/GET/chats/-chatId-/members/me) |

`read_all_messages` входит в документированные права администратора. Для обычного
участника `permissions` может отсутствовать; допустимо также `null`. Поэтому
отсутствие списка в отчёте означает неизвестное значение, а пустой список — отсутствие
явно объявленного права. Новое, неизвестное клиенту название права даёт
`invalid_response` и требует сверки обновлённого контракта. [Схема ChatMember](https://dev.max.ru/docs-api/objects/ChatMember).

Клиент сохраняет только используемые поля идентификации и прав, остальные поля
профиля игнорирует. В подписках проверяет тип массива и его элементов; внутренние
поля подписки не интерпретирует и не возвращает. Наличие записи подписки не доказывает
работоспособность адреса, правильность типов событий или доставку webhook.

## Запуск в тестовом окружении

Установите зависимости по README. Настройки читаются через `app.core.config.Settings`
из окружения или локального `.env`. Реальные токены следует добавить при настройке
окружения; в репозитории их нет. Не передавайте токен аргументом командной строки.

| Переменная | Назначение |
|---|---|
| `MAX_OBSERVER_TOKEN` | Токен Observer, нужен для `--bot observer` |
| `MAX_STAFF_TOKEN` | Токен Staff Bot, нужен для `--bot staff` |
| `MAX_API_BASE_URL` | По умолчанию `https://platform-api2.max.ru`; разрешён только этот HTTPS origin и порт 443 |
| `MAX_TIMEOUT_SECONDS` | Тайм-аут каждой сетевой фазы, по умолчанию 10 секунд |

После подготовки токенов выполните нужную команду:

```bash
uv run python -m app.integrations.max.probe --bot observer
uv run python -m app.integrations.max.probe --bot staff
```

Дополнительная проверка членства принимает ID тестового чата, уже известный команде.
В примере ниже `-456` — вымышленный ID; замените его своим:

```bash
uv run python -m app.integrations.max.probe --bot observer --chat-id=-456
```

Выполняются только перечисленные GET-запросы: без `--chat-id` их два, с ним — три.
Команда не создаёт подписки, не отправляет сообщения и не загружает переписку.
Членство сверяется с ID из `/me`.

MAX указывает актуальный домен `platform-api2.max.ru` и необходимость доверенного
сертификата Минцифры. Проверка TLS включена всегда. При необходимости администратор
окружения задаёт проверенный CA bundle через системную переменную `SSL_CERT_FILE`
или `SSL_CERT_DIR`, которые учитывает HTTPX. Это переменные процесса, а не поля
проектного `.env`; команда не отключает проверку сертификата и не устанавливает CA.
[Требования MAX](https://dev.max.ru/docs-api/methods/GET/me),
[настройка TLS HTTPX](https://www.python-httpx.org/advanced/ssl/).

## Интерпретация результата

`stdout` содержит JSON с ID бота, булевыми признаками и разрешёнными названиями прав.
Имена пользователей, сообщения, адреса подписок, токены и upstream-тексты ошибок
не печатаются. Пример **синтетического**, не полученного от реального бота результата:

```json
{
  "bot_id": 123,
  "is_bot": true,
  "has_subscriptions": false,
  "membership_checked": false,
  "is_admin": null,
  "permissions": null,
  "read_all_messages": null,
  "end_to_end_verified": false
}
```

Код `0` означает успешное выполнение запрошенной диагностики, даже если подписок
нет или право чтения не объявлено. Это не статус готовности интеграции.
`end_to_end_verified` всегда `false`: текущая команда не проверяет доставку событий.

При ошибке `stdout` пуст, `stderr` содержит только безопасный код:

| Код завершения | Значение |
|---|---|
| `2` | Нет токена (`missing_token`), неверные аргументы или настройки (`invalid_configuration`) |
| `1` | `unauthorized`, `access_denied`, `not_found`, `rate_limited`, `upstream_unavailable`, `http_error`, `unexpected_redirect`, `timeout`, `network_error` или `invalid_response` |

Редиректы не выполняются, автоматических повторов нет. При `rate_limited` повторите
диагностику позднее; `network_error` включает ошибки соединения и проверки TLS.
Невалидный JSON, неверные типы используемых полей и неожиданный ID бота завершаются
ошибкой. Неисправную подписку эта проверка определить не может.

## Проверка кода и следующий шаг

```bash
uv run python -m pytest tests/test_max_client.py
```

Тесты используют `httpx.MockTransport` и синтетические объекты по указанным схемам.
Проверяются оба токена CLI, пустые подписки, неизвестные права, ошибки доступа,
429, 5xx, тайм-ауты/TLS-ошибки, повреждённый JSON, перенаправления и отсутствие
секретов в отчётах, логах и отображаемых исключениях. Внешних сетевых вызовов к MAX
в этих тестах нет.

Для завершения P-02/P-03 потребуются отдельные испытания двух тестовых ботов:
получение сообщения через webhook, проверка секретного заголовка и повторной
доставки, callback, отправка и получение фото. Протокол испытаний должен содержать
обезличенные события, фактические результаты и оставшиеся ограничения.
