# Простой рабочий бот в MAX

Актуальное уточнение от 14 сентября 2026: продукт — один MAX-бот для жителей,
операторов и исполнителей. Веб-интерфейс и Mini App не входят в объём.

## Что видит житель

Неизвестный MAX ID не получает служебное меню. В личном диалоге доступны только
«Создать заявку» и «Мои заявки».

Создание заявки — четыре текстовых шага без справочников и вариантов:

1. Как вас зовут?
2. Напишите полный адрес.
3. Что произошло?
4. Телефон для связи.

После четвёртого ответа бот показывает сводку и две кнопки: «Подтвердить» и
«Отменить». До подтверждения заявка в CRM не создаётся. После подтверждения она
сразу получает начальный статус и оператору приходит карточка с именем, полным
адресом, телефоном, MAX ID и проблемой. В «Мои заявки» пользователь видит только
заявки, созданные его MAX ID, и упрощённый статус: «Принята», «В работе»,
«На проверке», «Выполнено» или «Передано оператору». После финального закрытия
появляется кнопка «Проблема осталась». Нажатие не создаёт новую заявку: текущая
заявка возвращается оператору с новой ревизией и сохраняет историю.

## Что делает оператор

Оператор получает диспетчерскую прямо в личном диалоге с тем же ботом:

- «Новые»;
- «Без исполнителя»;
- «В работе»;
- «Требуют внимания»;
- «Все заявки»;
- «Исполнители»;
- «Создать заявку».

В меню сразу показываются счётчики очередей. Оператор открывает заявку и нажимает
«Назначить исполнителя»; в списке показываются только активные сотрудники с
исполнительской ролью в БД. После назначения исполнитель сразу получает карточку задания.
Операторские очереди рассчитываются из общей таблицы заявок и существующих
статусов, отдельной копии заявок для диспетчера нет.

Оператор может вручную создать заявку: дом → категория → описание. Если доступен
только один дом или одна категория, соответствующий выбор пропускается.


## Что делает владелец

Владелец получает ту же диспетчерскую, что оператор, и отдельную кнопку
«Управление». Всё управление выполняется внутри MAX-бота, без Mini App.

В разделе «Сотрудники» владелец может добавить сотрудника по MAX ID, назначить
роль «Исполнитель» или «Оператор», поменять роль и отключить/включить доступ.
MAX ID владельца защищён от понижения роли и отключения через это меню.

В разделе «Чаты» показываются групповые чаты, в которых основной бот уже видел
сообщения. Анализ можно выключить для отдельного чата. В «Настройках» есть общий
выключатель анализа всех групповых чатов. Токен бота и webhook secret показываются
только как «настроен / не настроен»; их значения никогда не выводятся и меняются
только на сервере.

## Что делает исполнитель

Исполнитель видит только «Мои задания». В карточке видит адрес/описание, статус,
исполнителя и последние пояснения. Он может отметить «В работе» или «Готово»,
либо выбрать «Не выполнено» / «Для выполнения нужно…» и написать пояснение.
Исполнитель не получает диспетчерские очереди и не может распределять заявки.

Пояснение обязательно для «Не выполнено» и «Для выполнения нужно…», максимум
2000 символов. Нажатие исполнителем «Готово» не закрывает заявку окончательно:
для жителя она становится «На проверке», а у оператора попадает в
«Требуют внимания». Оператор из карточки нажимает «Закрыть заявку» либо
«Вернуть в работу». При устаревшей кнопке бот предлагает открыть свежую карточку;
старый результат не перезаписывается.

Команды `/start`, `/menu`, `/tasks`, `/new`, `/cancel` сохранены для
совместимости, но `/new` доступна только владельцу или оператору. Незавершённый
ввод истекает после 30 минут бездействия.

Основной бот можно добавить в групповой чат. Он не отвечает в общий чат и не
создаёт заявку автоматически. Webhook MAX только регистрирует чат и сохраняет
сообщение в очередь `chat_analysis_jobs`, после чего сразу отвечает MAX.

Отдельный процесс `app.bot.chat_analyzer` отправляет сообщение в DeepSeek V4 Flash.
Thinking включён явно, `reasoning_effort=max`, JSON-ответ строгий. Reasoning content
не сохраняется и не показывается оператору — используется только финальный JSON:
есть проблема или нет, краткая формулировка, confidence и severity.

При проблеме оператор получает только «MAX ID: … / Проблема: …». Одинаковый
повтор от того же пользователя в том же чате подавляется на 30 минут; разные
несрочные сигналы одного пользователя ограничиваются двухминутным cooldown.
Срочные разные сигналы cooldown обходят. Каждый реально отправленный сигнал
сохраняется отдельно от заявки для аудита, но автоматически заявку не создаёт.

Если DeepSeek временно недоступен, несрочное сообщение повторяется до трёх раз.
После исчерпания попыток текст очереди очищается. Для явной опасности
(газ, дым, искрение, прорыв/затопление, пожар, застрявшие люди) есть узкий
локальный emergency fallback, поэтому такой сигнал не ждёт восстановления API.
Старый endpoint Observer сохранён для совместимости, но для нового сценария
отдельный бот не нужен.

## Настройка при запуске

На dev-сервере реальные токены не нужны. На окружении с тестовыми ботами задаются:

| Переменная | Назначение |
|---|---|
| `MAX_STAFF_TOKEN` | Токен бота сотрудников, включая отправку личных ответов |
| `MAX_OBSERVER_TOKEN` | Токен бота домовых чатов |
| `MAX_STAFF_WEBHOOK_SECRET` | Отдельный случайный секрет подписки Staff |
| `MAX_OBSERVER_WEBHOOK_SECRET` | Другой случайный секрет подписки Observer |
| `MAX_OWNER_IDS` | MAX ID владельцев через запятую |
| `MAX_OPERATOR_IDS` | MAX ID операторов/диспетчеров через запятую |
| `MAX_EMPLOYEE_IDS` | MAX ID исполнителей через запятую |
| `MAX_BOT_ORGANIZATION_ID` | Организация, с которой работает этот экземпляр бота |
| `DEEPSEEK_API_KEY` | API key DeepSeek для анализа групповых чатов |
| `DEEPSEEK_MODEL` | `deepseek-v4-flash` |
| `DEEPSEEK_TIMEOUT_SECONDS` | Timeout отдельного анализатора, по умолчанию 120 секунд |
| `DEEPSEEK_MIN_CONFIDENCE` | Минимальная confidence для несрочного сигнала, по умолчанию 0.72 |

Секреты webhook состоят из 32–256 символов `A-Z`, `a-z`, `0-9`, `_`, `-`.
Например, каждый можно отдельно сгенерировать через `openssl rand -hex 32`.
Они должны различаться. Токены и секреты хранятся в env окружения, без Git.
Без токена и секрета соответствующий webhook возвращает `503`.

После запуска PostgreSQL и применения миграций настройте минимальный справочник:

```bash
uv run alembic upgrade head
uv run python -m app.bot.setup init --name 'Тестовая УК' --house 'Тестовая улица, 1'
```

Команда печатает `MAX_BOT_ORGANIZATION_ID`, ID домов и категорий. Сохраните ID
организации в env. Можно повторить `--house` для нескольких адресов.
Команда создаёт обычную категорию, первоначальный статус и сотрудников из env.
Владелец и `MAX_OPERATOR_IDS` при первом setup получают операторскую роль с
правом назначения; `MAX_EMPLOYEE_IDS` получают исполнительскую роль без права
распределения. Эти переменные являются bootstrap-списками: повторный setup не
перетирает роль, активность или scopes существующего сотрудника.
Доступ к другим организациям не появляется. При первом обращении сотрудника
заготовка имени `MAX <ID>` заменяется его именем в MAX.

Если справочник уже есть, передайте `--organization-id <UUID>`. Существующие сотрудники, их роли, блокировки и ограничения сохраняются. Новые
bootstrap ID из env могут быть добавлены повторным запуском команды, но обычное
управление сотрудниками после инициализации выполняется владельцем в боте.
Для сотрудников источником текущего bot-доступа является активная membership в БД;
удаление ID из bootstrap env само по себе существующую membership не удаляет.

Подключите известный ID домового чата к дому и категории из вывода настройки:

```bash
uv run python -m app.bot.setup bind-chat --chat-id=-456 --house-id <UUID> --category-id <UUID>
```

`-456` — вымышленный пример. Нужен фактический ID тестового чата.
Повторное одинаковое подключение допустимо. Перепривязка к другому дому запрещена,
поскольку изменила бы смысл уже сохранённых обращений.

При запуске через Compose те же команды выполняются через
`docker compose run --rm api python -m app.bot.setup …`.

## Приём и отправка событий

Сервер имеет два служебных адреса:

- `POST /api/bots/max/staff`: `bot_started`, `message_created`, `message_callback`;
- `POST /api/bots/max/observer`: `message_created`.

При деплое администратор регистрирует для каждого бота его HTTPS URL и `secret`
через [подписки MAX](https://dev.max.ru/docs-api/methods/POST/subscriptions).
Нужны HTTPS на порту 443 и доверенный сертификат. API сверяет заголовок
`X-Max-Bot-Api-Secret` до разбора тела. Локальный Compose сам HTTPS не публикует.

Ответ `200` означает, что событие и изменения сохранены в PostgreSQL либо событие
безопасно проигнорировано. При ошибке БД возвращается `503`, чтобы MAX повторил
доставку. Личные действия в группах и события от ботов игнорируются.
Callback без исходного сообщения не позволяет подтвердить личный диалог и также
игнорируется. Actor нажатия берётся из `callback.user`, а не из автора карточки.
[Форматы MAX](https://dev.max.ru/docs-api/objects/Update).

Ответы отправляет отдельный небольшой процесс:

```bash
uv run python -m app.bot.worker
# Или после настройки env и миграций:
docker compose --profile bot up -d --build api bot-worker chat-analyzer
```

Worker получает исключительно личные MAX `user_id`. Для сотрудников он снова проверяет
активную membership в текущей организации и изменения области доступа; для жителей
проверяет активность публичной учётной записи.
Используется один worker на БД, что обеспечивается advisory lock PostgreSQL.
Пауза 0,6 секунды между отправками ограничивает частоту ниже двух запросов в секунду.
Форматы сверены с [POST /messages](https://dev.max.ru/docs-api/methods/POST/messages)
и [POST /answers](https://dev.max.ru/docs-api/methods/POST/answers).
Текущая схема callback ACK принимает `{}`; поле `notification` в неё не входит.

При timeout, сетевой ошибке, `5xx` или падении процесса после начала отправки
доставка считается неопределённой. Автоматического повторения таких сообщений
нет: MAX мог уже принять ответ. Явные отказы также сохраняются для диагностики.
Сама заявка остаётся в БД; сотрудник может снова открыть список или карточку.
Сообщения старше 30 минут не отправляются. После попытки текст очереди очищается;
в очереди остаются состояние, безопасный код ошибки и идентификаторы.
Содержимое заявок и история пояснений продолжают храниться в профильных таблицах.

## Проверки и границы

Есть проверки полного рабочего цикла, повторной доставки, отзыва доступа,
переназначения и устаревших кнопок. Транспорт тестируется через MockTransport,
обработка и гонки — на отдельной PostgreSQL. Браузер и Mini App не нужны.
Существующий служебный API совместим с источниками `manual`, `staff_bot`, `chat`, `resident_bot`.

При деплое ещё нужно проверить реальные права основного бота на чтение групповых чатов, подписки,
личные отправки и callback ACK. Исполнителям и оператору нужно сначала открыть личный диалог с основным ботом. Массовая рассылка, вложения, SLA, расширенная аналитика и политика архивирования
не входят в эту поставку. AI используется только для фильтрации групповых сообщений.
На dev-сервере реальные сообщения не отправлялись и подписки не создавались.
