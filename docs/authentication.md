# Вход через MAX и первоначальный доступ

Это первый сценарий Э1: backend проверяет запуск мини-приложения MAX, создаёт
локальную идентичность сотрудника и выдаёт отзывную сессию. Реальные токены и ID
сотрудников добавляются в окружение при развёртывании. На dev-сервере без них
приложение запускается, а вход отвечает `503`.

## Конфигурация

| Переменная | Назначение | По умолчанию |
| --- | --- | --- |
| `MAX_STAFF_TOKEN` | Секретный токен Staff-бота, к которому привязано мини-приложение | Не задан |
| `MAX_OWNER_IDS` | MAX ID владельцев через запятую | Пустой список |
| `MAX_EMPLOYEE_IDS` | MAX ID обычных сотрудников через запятую | Пустой список |
| `MAX_INIT_DATA_TTL_SECONDS` | Максимальный возраст подписанных данных запуска | `300` |
| `MAX_INIT_DATA_FUTURE_SKEW_SECONDS` | Допустимое опережение часов MAX, секунд | `30` |
| `SESSION_TTL_SECONDS` | Срок сессии после входа, секунд | `28800` |
| `LOGIN_RATE_LIMIT` | Число попыток входа за окно отдельно на IP и подтверждённый MAX ID | `10` |
| `LOGIN_RATE_WINDOW_SECONDS` | Длительность окна ограничения, секунд | `60` |

ID — положительные целые числа до `9223372036854775807`. Например,
`MAX_OWNER_IDS=101,102` задаёт два синтетических ID; для настоящего окружения
нужны ID сотрудников. Если ID есть в обоих списках, применяются права владельца.
Токен Observer-бота не используется для входа. Секрет Staff-бота остаётся только
на сервере; клиенту передают собственный короткоживущий токен сессии.

После изменения окружения необходимо перезапустить все API-процессы.
На каждом защищённом запросе проверяются текущие списки ID и признак
`users.is_active`. Удалённый из обоих списков сотрудник теряет доступ, в том числе
по ранее выданной сессии. Перенос владельца только в список сотрудников снимает
его административные права. Роль не сохраняется в токене или таблице `users`.

## API

| Метод и путь | Запрос | Результат |
| --- | --- | --- |
| `POST /api/auth/max` | JSON `{"init_data":"<window.WebApp.initData>"}` | `200`: `access_token`, `token_type="bearer"`, `expires_at`, `user` |
| `GET /api/auth/me` | `Authorization: Bearer <access_token>` | `200`: текущий пользователь |
| `POST /api/auth/logout` | Тот же заголовок | `204`: текущая сессия отозвана |
| `GET /api/admin/users` | Сессия владельца, `limit` и `offset` | `200`: `items`, `limit`, `offset` |

Пользователь содержит только `id` (UUID), `max_user_id`, `display_name`,
`is_active`, вычисляемый `is_owner` и `created_at`. Параметры списка:
`limit=1..100`, по умолчанию `50`; `offset=0..10000`, по умолчанию `0`.
Список отсортирован по времени создания и UUID, пустая страница возвращает
`items: []`. Секреты, подписи и содержимое сессий в пользовательские ответы не входят.

Вход принимает исходную строку `window.WebApp.initData`, полученную через
[MAX Bridge](https://dev.max.ru/docs/webapps/bridge). Не нужно разбирать её
на клиенте или передавать `initDataUnsafe`: этот объект не подтверждает
подлинность пользователя. Backend принимает до 16 384 символов и 32 параметров.

Реализация следует [официальной проверке MAX](https://dev.max.ru/docs/webapps/validation):
значения URL-декодируются один раз, параметры сортируются, `hash` исключается
из подписываемой строки; ключ HMAC-SHA256 выводится из `WebAppData` и токена
Staff-бота. Подписи сравниваются за постоянное время. Повторяющиеся ключи,
неоднозначный JSON пользователя, некорректная кодировка и дата вне допустимого
интервала отклоняются. Неизвестные подписанные поля участвуют в проверке.

Локальные решения этого этапа: окно запуска 5 минут, допуск часов 30 секунд,
однократный обмен данных запуска на сессию и доступ только для ID из окружения.
Проверка подписи не вызывает внешний API MAX. Успешный первый вход автоматически
создаёт одну запись пользователя; повторные входы обновляют отображаемое имя.

## Сессии, повторные запросы и ошибки

Сессия — случайный непрозрачный токен с 256 битами энтропии. В PostgreSQL
сохраняются только его SHA-256, SHA-256 подписи использованного запуска,
срок действия и время отзыва. Уникальное ограничение на отпечаток запуска
защищает от повторного входа после перезапуска Redis. При каждом обращении
проверяются срок, отзыв, активность сотрудника и актуальные списки доступа.

Redis ограничивает запросы атомарным счётчиком с TTL и однократно резервирует
подписанный запуск. Он не хранит исходные `initData`, токен Staff-бота или сессии.
Без Redis вход закрыт. Проверки уже выданных сессий используют PostgreSQL.
IP берётся из ASGI-клиента запроса; доверие к прокси задаётся инфраструктурой,
произвольный `X-Forwarded-For` приложение не разбирает.

Один `initData` можно обменять на сессию только один раз. После выхода,
истечения сессии, потери ответа на вход или временного сбоя БД после резервирования
запуска нужно заново открыть мини-приложение в MAX и получить свежие параметры.
Клиент должен сохранять полученный токен в памяти текущего приложения и передавать его
в заголовке. Ответы приватного API имеют `Cache-Control: no-store`.

| Код | Значение |
| --- | --- |
| `401` | Неверная подпись/сессия, старый или повторный запуск, неразрешённый ID, отключённый сотрудник |
| `403` | Сотрудник аутентифицирован, но действие требует владельца |
| `422` | Некорректная структура запроса или параметры пагинации |
| `429` | Превышен лимит входа; время ожидания в секундах передаётся в `Retry-After` |
| `503` | Не настроен вход либо временно недоступна необходимая инфраструктура |

Ошибки не содержат исходный запрос или подробности драйверов. Аудит сохраняет
события `user.created`, `auth.login`, `auth.logout` с внутренними UUID и временем,
без токенов, полных данных запуска и профиля MAX. API для изменения аудита нет.

## Схема и проверка

Миграция `0001_identity` создаёт `users`, `auth_sessions`, `audit_logs`.
Применение на подготовленной dev/test БД: `uv run alembic upgrade head`.
Актуальность схемы: `uv run alembic check`. Приложение не запускает миграции
автоматически. Команды настройки БД и запуска приведены в [README](../README.md).

`uv run pytest tests/test_identity.py` проверяет подпись на синтетических данных,
включая независимый вектор Node crypto, изменения полей и граничный возраст.
`uv run pytest tests/test_auth.py` требует отдельные `TEST_DATABASE_URL` и
`TEST_REDIS_URL`; проверяет вход/выход, доступ владельца, отзыв, удаление из env,
постоянную защиту от повторного запуска, ограничения Redis и безопасные ошибки.
Без этих переменных интеграционные проверки явно пропускаются. Реальные токены
и обращения к MAX в тестах не используются.

## Дальнейший объём

Это основание аутентификации и начальной проверки доступа. Э2 должен добавить
сотрудников и настраиваемые роли через админку, области организаций и домов,
правила привилегированных изменений и расширенный аудит. Списки env сейчас
управляют первоначальным доступом; полноценная модель RBAC ещё не реализована.
Frontend, проверка реального запуска MAX и production-развёртывание остаются
отдельными задачами. Перед очисткой сессий нужно сохранить отпечатки запусков
как минимум на весь срок их допустимости; автоматическая очистка здесь не добавлена.
