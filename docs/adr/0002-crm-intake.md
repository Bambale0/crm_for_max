# ADR 0002: регистрация заявок и области доступа

Дата: 2026-09-13. Статус: принято для ограниченной поставки Э2.
Продолжает [основу backend](0001-backend-foundation.md); API описан
в [инструкции ручной регистрации](../crm-intake.md).

## Граница поставки

ТЗ §20 задаёт иерархию, §18–19 — области доступа и разрешения, §38 — ручной
ввод, §12 — настраиваемые статусы. Граф переходов, доступность исполнителей
и приоритеты маршрутизации ещё не определены. Поэтому эта поставка реализует
подготовку каталога, регистрацию, поиск и просмотр заявки с первоначальной
историей. Назначение и переходы сюда не входят.

## Решения

MAX env остаётся условием входа. Для сотрудника добавляется отдельная запись
в организации с ролью и областью доступа. MAX ID связывает её с вошедшим
пользователем, поэтому запись можно создать до первого входа. Членство не
обходит allowlist env. Владелец из env сохраняет полный контроль системы.

В этой поставке каталог и настройки доступа изменяет только владелец.
Пользовательские роли настраивают четыре реализованных разрешения: просмотр
домов, собственного профиля сотрудника, просмотр и создание заявок.
Делегированное администрирование добавляется после уточнения матрицы прав.
Это ограниченная начальная модель, а не полная permission system из ТЗ.

Роль задаётся данными, а не Python Enum должностей. Разрешения и UUID областей
хранятся в JSONB-массивах с проверкой структуры в БД и значений в API.
Права, активность сотрудника и области перечитываются при каждом обращении.
Пустые списки домов и категорий запрещают доступ. Широкий доступ выражается
явными флагами; ограничение участка применяется дополнительно через И.

Списки фильтруются до пагинации. Карточка и история скрывают недоступные
объекты ответом 404. Ссылки иерархии защищены составными FK по организации;
для подъезда заявки проверяется также конкретный дом. Идентификаторы связей
нельзя использовать для обращения к данным чужой организации.

Статусы хранятся в таблице: организация получает «Новую», владелец может
добавить другие статусы без изменения кода. Частичный уникальный индекс
разрешает не более одного первоначального статуса на организацию. В текущем
API нельзя менять статус заявки; будущий граф переходов станет отдельными
данными и бизнес-правилами.

Ручное создание требует UUID Idempotency-Key. Уникальность по организации,
автору и ключу, нормализованный хеш данных и PostgreSQL ON CONFLICT защищают
от дублей при сетевых повторах и конкуренции. История и аудит сохраняются
в той же транзакции. Контакты и описание не дублируются в аудит или HTTP-логи.

## Последствия

Миграция 0002 дополняет 0001, не переписывая существующие учётные записи и
сессии. Заявки имеют глобальные номера с возможными пропусками. Организации
и адреса не считаются уникальными по тексту; связи выбираются по UUID.
Интерфейсу нужно предложить явный выбор дома и повторить отправку с тем же
ключом при потере ответа. Реальные MAX-токены и production-операции для
разработки и автоматических проверок не требуются.
