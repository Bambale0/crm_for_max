# ADR 0001: основа backend и вход через MAX

Дата: 2026-09-13. Статус: принято для первой поставки на dev-сервере.
Связь: [Э0](../epics/E0.md), [Э1](../epics/E1.md).

## Решение

Backend — Python 3.12, FastAPI, SQLAlchemy async, PostgreSQL и Alembic.
Redis хранит временные ограничения частоты входа и отметки использования
подписанных данных запуска. Зависимости фиксируются в `uv.lock`.
Приложение создаётся фабрикой: конфигурация передаётся явно, пулы соединений
открываются и закрываются через lifespan. Миграции запускаются отдельно.

HTTP-адаптеры находятся в `app/api` и `app/auth/routes.py`, операции входа —
в `app/auth`, инфраструктура — в `app/core`, модели — в `app/models`.
Клиент MAX изолирован в `app/integrations/max`; его диагностика выполняет
только GET-запросы и не меняет подписки или содержимое чатов.

По решению заказчика сотрудники входят через MAX; настройки передаются через
env при деплое. Backend принимает исходную строку `window.WebApp.initData`
из Mini App, проверяет подпись токеном Staff Bot и свежесть данных. Прикладное
право входа определяется отдельно списками `MAX_OWNER_IDS` и
`MAX_EMPLOYEE_IDS`. Проверенный MAX ID вне этих списков не даёт доступа в CRM.
Подробный контракт находится в [описании авторизации](../authentication.md).

Для обычных API-запросов выдаётся ограниченная по времени отзываемая сессия.
В БД хранятся хеш случайного токена и уникальный хеш подписи использованных
данных запуска. Поэтому перезапуск Redis не разрешает повторный обмен тех же
initData на сессию. Исходные initData и токены ботов не сохраняются.
Проверка текущего env выполняется и для действующих сессий.
Изменение env требует перезапуска всех экземпляров приложения.

В этой поставке есть только базовое различие владельца и сотрудника.
Иерархия УК, подразделения, участки и разрешения по домам будут добавлены
в последующих задачах; текущий список сотрудников не является полной RBAC.

## Проверки и последствия

Автотесты используют синтетические подписи MAX и отдельные PostgreSQL/Redis.
SQL-тесты откатывают внешнюю транзакцию, включая операции с внутренним commit.
Миграции проверяются на отдельной тестовой базе до тестов. CI также проверяет
стиль, типы, Compose и сборку образа.

`/health/live` подтверждает работу процесса; `/health/ready` проверяет
подключения к PostgreSQL и Redis. Readiness не проверяет правильность миграций
или реальные права MAX. Ошибки зависимостей не раскрывают строки подключения.
HTTP-журнал содержит сгенерированный request ID, метод, шаблон маршрута,
статус и длительность; тела, query string и заголовки в него не включаются.

Без MAX env backend запускается, но вход возвращает 503. Сборка и автотесты
выполняются без рабочих токенов. Это позволяет продолжать разработку до
подготовки интеграционного окружения.

## Следующие задачи

- Подключить экран Mini App к API входа и проверить реальный запуск в MAX.
- Проверить два бота, тестовый чат, доставку событий и права согласно Э0.
- Уточнить модель организаций и разрешений перед добавлением доменных таблиц.
- Добавить основной каталог CRM, заявки и историю изменений по Э2.
- Подготовить очередь, хранилище вложений и приём событий по Э1/Э3.

Эта поставка не закрывает целиком Э0 или Э1 и не включает production-деплой.

## Основания

Контракт подписи сверяется с официальной
[валидацией MAX](https://dev.max.ru/docs/webapps/validation) и
[MAX Bridge](https://dev.max.ru/docs/webapps/bridge).
Жизненный цикл следует [FastAPI lifespan](https://fastapi.tiangolo.com/advanced/events/),
пулы и сессии — [SQLAlchemy asyncio](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html).
