# Ручная регистрация заявки через API

Эта поставка добавляет справочники, роли и области доступа, ручное создание,
список, карточку и начальную историю заявки. Интерфейс оператора, назначение,
переходы статусов, комментарии и SLA будут добавлены отдельными задачами Э2.

## Подготовка

Запуск PostgreSQL, Redis и API описан в [инструкции разработчика](development.md).
Примените `uv run alembic upgrade head` к своей dev/test БД: миграция
`0002_crm_intake` добавляет каталог и заявки поверх `0001_identity`, сохраняет
учётные записи и сессии. В `audit_logs` добавлены nullable `target_type` и
`target_id`, чтобы связывать события с объектом CRM без хранения текста заявки.

Для работы API нужен токен сессии, полученный при [входе через MAX](authentication.md).
На всех запросах передавайте `Authorization: Bearer <access_token>`.
Рабочие MAX env по-прежнему добавляются при деплое. Автотестам они не нужны.

## Кто получает доступ

В этой поставке справочники и настройки доступа изменяет только владелец
из `MAX_OWNER_IDS`. Сотрудник может работать с заявками, когда одновременно:

1. Его MAX ID разрешён для входа текущим env.
2. Есть активная запись сотрудника в выбранной организации.
3. У его роли есть разрешение на действие.
4. Объект входит в разрешённые участок, дома и категории.

Для оператора создайте роль с `houses.view`, `requests.view`, `requests.create`.
Дополнительное `employees.view` позволяет сотруднику видеть собственную запись
в справочнике сотрудников. Владелец видит все записи. Это весь поддержанный
набор разрешений данной поставки; неизвестные разрешения отклоняются.
`requests.create` само по себе не даёт чтения списков заявок и справочников.

Области доступа комбинируются через **И**. `area_id`, если задан, ограничивает
участок. `house_ids` и `category_ids` задают списки доступных объектов.
Пустой список запрещает доступ. Явные `all_houses=true` и `all_categories=true`
снимают соответствующий список, но сохраняют границу организации и участка.
Дом в `house_ids` должен относиться к заданному участку, если участок указан.

Изменение роли, деактивация сотрудника и изменение областей действуют на
последующие запросы уже выданной сессии. Новый вход не требуется. Настройка
сотрудника через API не добавляет его MAX ID в env автоматически.

## Справочники

Все перечисленные коллекции поддерживают `GET` и `POST`. При создании ответ —
`201` с созданной записью. Значения ниже описывают поля JSON; UUID берутся
из предыдущих ответов API.

| Путь | Поля создания |
| --- | --- |
| `/api/organizations` | `name` |
| `/api/districts` | `organization_id`, `name` |
| `/api/areas` | `organization_id`, `district_id`, `name` |
| `/api/houses` | `organization_id`, `area_id`, `address` |
| `/api/entrances` | `organization_id`, `house_id`, `number` |
| `/api/categories` | `organization_id`, `name` |
| `/api/roles` | `organization_id`, `name`, `permissions` — список строк |
| `/api/employees` | `organization_id`, `max_user_id`, `display_name`, `role_id`; необязательные поля областей доступа ниже |
| `/api/statuses` | `organization_id`, `name`, `code`; необязательный `is_initial`, по умолчанию `false` |

Создавайте записи в порядке таблицы. Организация автоматически получает
первоначальный статус `new` / «Новая». Можно добавлять дополнительные статусы;
код — латинская буква, затем латинские буквы, цифры и `_`, до 64 символов.
В организации допускается только один первоначальный статус. Добавленные
статусы пока не назначаются заявкам: API переходов ещё не реализован.

Пример записи сотрудника с ограничениями:

```json
{
  "organization_id": "<UUID организации>",
  "max_user_id": 202,
  "display_name": "Тестовый оператор",
  "role_id": "<UUID роли>",
  "is_active": true,
  "area_id": "<UUID участка>",
  "all_houses": false,
  "all_categories": false,
  "house_ids": ["<UUID дома>"],
  "category_ids": ["<UUID категории>"]
}
```

UUID в угловых скобках — обозначения, их нужно заменить значениями ответов.
MAX ID `202` — синтетический пример. Если области не переданы, списки пусты,
оба `all_*` равны `false`; карточка сотрудника сама по себе не открывает заявки.

`PATCH /api/roles/{id}?organization_id=<UUID>` меняет `name` и/или `permissions`.
`PATCH /api/employees/{id}?organization_id=<UUID>` меняет имя, роль, активность,
участок и области доступа. Для снятия ограничения участка передайте `area_id:null`.
Для очистки списка передайте `[]`; `null` для остальных полей запрещён.
MAX ID и организация сотрудника через PATCH не меняются. Изменения атомарны,
записываются в аудит с автором и идентификатором объекта.

Для GET, кроме списка организаций, обязателен `organization_id` в query.
Списки имеют `limit=1..100` (по умолчанию 50) и `offset=0..10000` (по умолчанию 0).
Ответ: `{"items":[...],"limit":50,"offset":0}`. Ограничения доступа применяются
до пагинации. Пользователь без членства не видит организацию в списке.

`houses.view` открывает разрешённые дома, их подъезды, участки и районы;
`requests.view` — категории из области доступа и статусы своей организации.
`GET /api/roles` и `GET /api/permissions` доступны только владельцу.
Поиск адреса: `GET /api/houses?organization_id=<UUID>&q=Тестовая`.
Подъезды выбранного дома: `/api/entrances?organization_id=<UUID>&house_id=<UUID>`.
Адрес не является уникальным ключом; оператор выбирает конкретный дом.

## Создание заявки

Отправьте `POST /api/requests` с `Idempotency-Key: <новый UUID>` и JSON:

```json
{
  "organization_id": "<UUID организации>",
  "house_id": "<UUID дома>",
  "entrance_id": null,
  "category_id": "<UUID категории>",
  "applicant_name": "Тестовый заявитель",
  "applicant_phone": "+70000000000",
  "apartment": "12",
  "description": "Не работает освещение в подъезде",
  "priority": "normal"
}
```

Обязательны организация, дом, категория и непустое описание до 10 000 символов.
Подъезд, заявитель, телефон и квартира необязательны. Чтобы не указывать подъезд,
опустите поле или передайте JSON `null`. Приоритет: `critical`, `high`, `normal`
или `low`; по умолчанию `normal`. Неизвестные поля отклоняются.

Сервер проверяет принадлежность дома, подъезда и категории организации;
подъезд дополнительно должен принадлежать выбранному дому. Участок выводится
из дома, а первоначальный статус — из справочника организации. Ввод произвольного
`area_id`, `status_id`, исполнителя или срока SLA здесь не предусмотрен.

Первое сохранение возвращает `201`, карточку и заголовок `Location`.
Номер генерирует PostgreSQL; поле `code` имеет вид `REQ-00001`. Номера общие
для системы, могут содержать пропуски после откатов и конфликтов.
Создание, первоначальная история статуса и событие аудита фиксируются одной
транзакцией. Ошибка сохранения истории откатывает весь результат.

Один `Idempotency-Key` используйте для одной отправляемой заявки. После
потери ответа повторяйте запрос с тем же ключом и теми же данными. Повтор
возвращает `200` и существующую заявку. Другие данные с тем же ключом дают
`409`. Ключ ограничен организацией и автором; одинаковые одновременные
запросы создают одну запись. Повтор тоже проверяет актуальные права доступа.
Для новой заявки создавайте новый UUID.

## Просмотр и поиск

- `GET /api/requests?organization_id=<UUID>` — доступные заявки, новые сначала.
- `GET /api/requests/{id}` — карточка.
- `GET /api/requests/{id}/history` — первоначальная запись истории с автором,
  временем и идентификаторами статусов; ответ `{"items":[...]}`.

Список поддерживает `limit`, `offset`, `house_id`, `category_id`, `status_id`,
`priority`, `created_from`, `created_to` и `q` (до 200 символов).
Даты ISO 8601 должны содержать часовой пояс; границы включаются в выборку.
`q` ищет подстроку описания, имени, телефона и квартиры либо точный номер
`REQ-00001` / `1`. `%` и `_` трактуются как обычные символы. Адрес ищется
в справочнике домов; найденный `house_id` передаётся в фильтр заявок.

Все ответы API имеют `Cache-Control: no-store`. Тексты заявок и контакты не
попадают в журнал HTTP; аудит хранит действие, автора и ссылку на объект.
История и карточка проверяют те же области доступа, что и список.

| Код | Причина |
| --- | --- |
| `401` | Нет действующей сессии или MAX ID больше не разрешён env |
| `403` | Недостаточно разрешений или попытка создать заявку вне своей области |
| `404` | Объект/организация отсутствует либо недоступен текущему сотруднику |
| `409` | Повтор ключа с другими данными, дубликат MAX ID в организации, второй первоначальный статус или отсутствие первоначального статуса |
| `422` | Неверные поля, UUID, ссылка на чужого родителя, несовместимая область или отсутствующий Idempotency-Key |
| `503` | Временная ошибка необходимой инфраструктуры |

## Проверки и дальнейший объём

`uv run pytest` с отдельными `TEST_DATABASE_URL` и `TEST_REDIS_URL` проверяет
области доступа, IDOR, отзыв прав, атомарность, повторные и конкурентные запросы.
Обычные тесты откатывают внешнюю транзакцию. Два теста конкуренции создают
уникальные схемы с синтетическими данными в тестовой PostgreSQL и не удаляют
таблицы или чужие записи. Эти схемы исчезают вместе с одноразовым контейнером.
